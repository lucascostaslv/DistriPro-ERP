Levantamento completo e detalhado de TODAS as funcionalidades atualmente
implementadas no sistema DistriPro-ERP, como preparação para uma refatoração
completa do sistema. O foco é exclusivamente em COMPORTAMENTO e REGRAS DE

Como este documento foi produzido
-----------------------------------
Leitura integral do código-fonte de produção (`src/App.js` e todos os módulos
em `src/`), módulo por módulo, extraindo o comportamento funcional efetivo do
código (não a intenção original nem a documentação — o que o código realmente
faz hoje, incluindo bugs e inconsistências relevantes, sinalizados ao longo do
texto e consolidados no Apêndice A).

- "Firestore" = banco de dados principal (tempo real, multi-tenant por loja,

  específicos (perfis tributários, clientes/fornecedores, notas fiscais

1. ARQUITETURA MULTI-TENANT E SESSÃO
================================================================================

O sistema é multi-tenant: cada loja (tenant) tem seus dados operacionais
isolados sob o caminho `/artifacts/{lojaId}/public/data/{coleção}` dentro de
um único projeto Firestore administrativo compartilhado. Um segundo mecanismo,
mais antigo e usado apenas para o documento `store/data` (dados de
configuração básica da loja, como `companyInfo`), utiliza projetos Firebase
separados por loja (`firebaseConfig` individual, cacheado por instância).
Coleções de nível "administrativo" (`stores`, `users`, `settings`) vivem fora
do namespace de tenant, no projeto Firebase administrativo central.

O contexto global (`TenantContext`) expõe `currentStore`, `currentUser` e um
objeto `tenantDB` que abstrai leitura/escrita tanto no Firestore (namespace do
tenant) quanto no Supabase (filtrando automaticamente por `firebase_store_id`
da loja ativa) — todos os módulos do sistema usam essa camada para não
precisar montar caminhos/queries manualmente.

Sessão do usuário é persistida em `localStorage` (chave `distripro_session`)
com timestamp de criação e expira após 12 horas; ao expirar, a chave é
removida e o usuário volta à tela de login. Há dois modos de sessão distintos:
"user" (login de operador de uma loja específica) e "superadmin" (login do
super administrador, sem vínculo a loja).


================================================================================
2. AUTENTICAÇÃO (LOGIN)
================================================================================

Tela única de login serve tanto para usuários de loja quanto para o Super
Administrador, usando o mesmo formulário de usuário/senha (sem seletor de
loja — a loja é resolvida implicitamente a partir do cadastro do usuário).

Fluxo de submissão (nesta ordem, a cada tentativa de login):

1. TENTATIVA COMO SUPER ADMIN (sempre verificada primeiro)
   - Busca o documento `settings/superadmin` na base administrativa.
   - Se existir, usa as credenciais gravadas nele; se não existir, usa as
     credenciais padrão fixas no código: usuário "superadmin", senha
     "superadminn".
   - Se bater, autentica como super admin e encerra o fluxo (não tenta login
     de loja).
   - Se a leitura do Firestore falhar (erro de conexão), ainda tenta
     autenticar contra as credenciais padrão hardcoded diretamente, sem
     depender do banco (resiliência de fallback).

2. LOGIN DE USUÁRIO DE LOJA (só tentado se não bateu como super admin)
   - Consulta a coleção `users` (base administrativa) filtrando por
     `username` E `password` iguais (comparação de igualdade direta —
     senhas armazenadas e comparadas em TEXTO PURO, sem hashing).
   - Usa o primeiro resultado encontrado.
   - Se nenhum usuário for encontrado: erro "Credenciais inválidas!".
   - Se o usuário existir mas estiver com `active: false`: bloqueia com
     "Este usuário está desativado. Contate o suporte." (nem chega a
     verificar a loja).
   - Se o usuário estiver ativo, busca a loja correspondente ao `storeId`
     gravado no cadastro do usuário:
     - Loja não encontrada → erro "Configuração da loja não encontrada."
     - Loja encontrada mas `active === false` → bloqueia com "Esta loja
       está desativada. Contate o suporte." — isso barra TODOS os usuários
       daquela loja simultaneamente, mesmo que individualmente estejam
       ativos.
     - Loja ativa → login efetivado, repassando a configuração completa da
       loja e o usuário autenticado ao restante do app.
   - Erros inesperados de conexão mostram "Erro ao conectar com o banco de
     dados de usuários."

Validações: não há validação client-side de formato/tamanho mínimo de
usuário/senha — qualquer valor (inclusive vazio) é enviado à consulta; toda a
validação de fato ocorre no retorno da query.

Sem escrita no banco durante o login — é uma operação somente leitura; a
persistência da sessão fica a cargo do componente raiz (`App`).

3. PAINEL SUPER ADMINISTRADOR
================================================================================

Console central para o Super Admin gerenciar todas as lojas (tenants) e seus
usuários, e configurar qual provedor de integração fiscal cada loja utiliza.

3.1 Listagem de lojas e usuários
   - Ao carregar, busca TODAS as lojas em `stores` (campo `active` tratado
     como `true` quando ausente/não explicitamente `false`) e TODOS os
     usuários em `users`, fazendo o "join" em memória (usuários filtrados por
     `storeId` de cada loja).
   - Também carrega as credenciais do próprio super admin de
     `settings/superadmin` (ou usa o padrão fixo se o documento não existir).
   - Cada loja é exibida com nome, ID, badge de status (Ativa/Inativa) e a
     tabela de usuários vinculados (usuário, senha, status, ações).

3.2 Ativar/Desativar loja
   - Pede confirmação (`window.confirm`) antes de agir.
   - Inverte o campo `active` do documento da loja.
   - Efeito direto: desativar a loja bloqueia o login de TODOS os usuários
     vinculados a ela (ver seção 2).

3.3 Mostrar/ocultar senha de usuário
   - Toggle puramente de exibição (não altera dados) — alterna entre mostrar
     a senha em texto puro ou "••••••" na listagem.

3.4 Editar usuário de loja
   - Modal com campos Usuário e Senha, ambos obrigatórios (bloqueia com
     "Preencha todos os campos." se algum estiver vazio — não há outras
     validações, como tamanho mínimo).
   - Sobrescreve `username`/`password` do documento em texto puro.

3.5 Ativar/Desativar (bloquear) usuário
   - Sem diálogo de confirmação — inverte diretamente o campo `active`.
   - Usuário bloqueado tem login impedido (ver seção 2).

3.6 Configurações do próprio Super Admin
   - Modal separado (ícone de engrenagem) permite editar o próprio
     usuário/senha de acesso do Super Admin.
   - Sobrescreve integralmente (sem merge parcial) o documento
     `settings/superadmin`. Não valida campos vazios aqui.

3.7 Modal "Integração / Manutenção" por loja
   Acionado pelo botão de engrenagem ao lado de cada loja.

   Abertura: define a loja em gestão, reseta a aba ativa para "Bling",
   define o `currentStore` do contexto global como `{id: loja.id}` (para
   que os painéis internos consigam operar sobre aquela loja específica), e
   consulta a tabela Supabase `fiscal_provider_settings` para descobrir o
   provedor fiscal atualmente configurado (padrão "bling" se não houver
   registro ou a consulta falhar).

   Fechamento: limpa a loja em gestão e limpa o `currentStore` do contexto
   global (evita que outras partes do app continuem "vendo" essa loja).

   TOGGLE DE PROVEDOR DE EMISSÃO FISCAL (Bling × BrasilNFe legado):
   - Dois botões mutuamente exclusivos: "Bling" e "BrasilNFe (legado)"; o
     provedor ativo é destacado.
   - Ao clicar em um provedor diferente do atual, grava/atualiza (upsert,
     `onConflict: firebase_store_id` — um único registro por loja) na
     tabela Supabase `fiscal_provider_settings` os campos
     `firebase_store_id`, `provider` e `updated_at`.
   - Clicar no provedor já ativo, ou sem loja selecionada, não faz nada.
   - Durante a gravação os botões ficam desabilitados; sucesso mostra toast
     confirmando o novo provedor; erro mostra a mensagem da falha.
   - Texto explicativo fixo no painel esclarece que essa escolha só define
     QUAL integração o PDV da loja usa para emitir notas — a configuração
     de credenciais de cada provedor (Bling na aba ao lado, ou o
     Certificado Digital nas Configurações da loja, para o BrasilNFe)
     precisa ser preenchida separadamente.
   - Esse valor é consultado em tempo de execução pelo app da loja (ver
     seção 7) sempre que uma venda é processada ou uma nota é emitida.

   Aba "Integração Fiscal (Bling)": delega ao componente
   `BlingIntegrationPanel` (ver seção 7.2) — cadastro de credenciais OAuth
   do Bling, fluxo de conexão, e mapeamento de referências (natureza de
   operação, formas de pagamento) necessárias para emitir.

   Aba "Manutenção": delega ao componente `MaintenancePanel` (ver seção
   7.3) — reset de dados operacionais e zerar quantidade em estoque de uma
   loja específica; restrito ao Super Admin (não aparece nas Configurações
   da própria loja).

   Reabertura automática pós-OAuth: depois que a lista de lojas carrega, o
   painel verifica se existe a chave `bling_reopen_store_id` no
   `sessionStorage` (gravada pelo callback de retorno do OAuth do Bling, ver
   seção 7.2) e, se existir, reabre automaticamente o modal de gestão da
   loja correspondente — necessário porque o redirecionamento de página
   inteira do fluxo OAuth do Bling recarrega toda a SPA e perde o estado em
   memória do super admin que estava configurando aquela loja.

3.8 Callback OAuth do Bling (nível raiz do App, mas funcionalmente parte
    deste fluxo administrativo — ver detalhamento completo na seção 7.2).

4. DASHBOARD
================================================================================

4.1 KPI — Faturamento: soma do campo `total` de todas as vendas recebidas
    (o filtro de período é responsabilidade de quem alimenta o componente).

4.2 KPI — Lucro Estimado: soma do campo `profit` já calculado no momento de
    cada venda (não é recalculado aqui).

4.3 KPI — Vendas Hoje: contagem de vendas cuja data corresponde ao dia atual.

4.4 KPI — Estoque Baixo: conta produtos com estoque disponível ≤ limite
    mínimo configurado (`minStock`, padrão 5 se ausente). Produtos do tipo
    "pack" (caixa/fardo) são EXCLUÍDOS deste cálculo, pois seu estoque é
    sempre virtual (derivado do produto pai — ver regra de conversão na
    seção 5.3/11).

4.5 Alerta de Cobrança "para Hoje": filtra vendas fiado cujo vencimento é
    hoje; mostra até 3 clientes com valor, com link para abrir o item
    específico em Contas a Receber; botão "Ver todos" navega sem filtro.

4.6 Widget de Saldo Bancário: lista cada conta com saldo atual (destacado em
    vermelho se negativo) e tipo (Caixa Físico/Poupança/Corrente); card de
    Total Consolidado somando todas as contas.

4.7 Gráfico de Fluxo de Caixa Diário: soma de vendas por dia nos últimos 7
    dias, escala proporcional ao maior valor do período.

4.8 Alertas de Estoque (lista detalhada): reaproveita a lista de itens com
    estoque baixo, mostrando estoque atual vs. mínimo configurado por item;
    mensagem de "tudo certo" quando não há itens críticos.


================================================================================
5. PDV — PONTO DE VENDA
================================================================================

Núcleo operacional do sistema — maior e mais crítico módulo.

5.1 SESSÃO DE CAIXA (abertura/fechamento controlados dentro do PDV)

   Verificação automática ao entrar no PDV: checa se o operador logado já
   tem sessão de caixa aberta (`CaixaService.checkOpenSession`). Se não
   tiver, carrega a lista de caixas cadastrados, pré-seleciona o primeiro e
   preenche o "fundo de troco" sugerido com o saldo residual daquele caixa
   (herdado do fechamento anterior), abrindo automaticamente o modal de
   Abertura de Caixa.

   Abertura de Caixa: usuário escolhe um caixa físico e informa o "Dinheiro
   Inicial na Gaveta" (pré-preenchido se houver saldo residual). Bloqueia
   com instrução para cadastrar em Configurações se não houver nenhum caixa
   cadastrado. TODA tentativa de adicionar produto ao carrinho ou iniciar
   pagamento exige sessão aberta — caso contrário bloqueia com "Abra o
   caixa antes de vender [F10]." e reabre o modal automaticamente.

   Fechamento de Caixa (fluxo em 2 etapas — "summary" → "deposit"):
   - Summary: busca vendas da sessão (excluindo perdas `isLoss`),
     movimentações de sangria da sessão e contas bancárias. Agrupa total
     vendido por forma de pagamento (considerando também vendas com múltiplas
     formas). Calcula total de vendas, total de sangrias, e "Dinheiro
     Estimado na Gaveta" = saldo inicial + total em Dinheiro − sangrias.
   - Deposit: permite (opcional) registrar retirada/depósito — valor
     (limitado ao dinheiro estimado disponível), destino (conta bancária
     cadastrada ou "Outros — envelope/cofre"), observação (obrigatória se
     destino = "Outros"). Calcula em tempo real o saldo residual que ficará
     na gaveta (nunca negativo).
   - Ao confirmar: chama `CaixaService.closeSession` com os totais; se houve
     retirada com destino real em conta bancária, grava entrada em
     `account_transactions` e incrementa o saldo da conta de destino — o
     dinheiro "sai da gaveta" e "entra" contabilmente na conta escolhida.
     Imprime automaticamente um relatório de fechamento (cupom térmico
     80mm) com totais por forma de pagamento, sangrias detalhadas, valor
     retirado e saldo residual.

5.2 BUSCA E ADIÇÃO DE PRODUTOS AO CARRINHO

   Busca reativa a partir de 2 caracteres: filtra por nome (contém,
   case-insensitive), código interno, código de barras principal ou
   qualquer código de barras extra; limita a 8 resultados. Itens do tipo
   "supply" (insumo) só aparecem se tiverem `isCheckoutEnabled === true`;
   produtos de revenda comuns sempre aparecem.

   Atalho de "quantidade rápida": digitar um padrão como "5*" ou "5x" no
   campo de busca define a quantidade a adicionar como 5 e limpa o campo
   (pensado para leitor de código de barras físico).

   Navegação por teclado no dropdown: setas movem seleção, Enter confirma
   — com esta ordem de prioridade ao pressionar Enter sem navegação prévia:
   (1) item destacado por seta; (2) correspondência EXATA de código
   (bipagem); (3) se sobrou exatamente 1 resultado no filtro, esse.

   Atalho global F12: alterna foco/limpeza do campo de busca a qualquer
   momento (liga/desliga "modo bipagem").

   Adição ao carrinho — validações: exige sessão de caixa aberta; verifica
   estoque disponível — se insuficiente e o usuário NÃO tiver a permissão
   `can_sell_without_stock`, bloqueia ("Estoque insuficiente! Disponível:
   X"); se o usuário TIVER essa permissão, permite mesmo assim com aviso
   explícito ("venda permitida para este usuário").

   Alteração de quantidade no carrinho: incremento revalida estoque
   disponível (resolvendo produto original em caso de pack) e bloqueia
   "Estoque máximo atingido." nas mesmas condições acima; decremento a 0 ou
   menos remove o item automaticamente.

   Remoção de item: direta, sem confirmação. Limpar carrinho: pede
   confirmação, zera carrinho, forma de pagamento e entradas de pagamento.

5.3 PRODUTOS "PACK" (CAIXA/FARDO) × UNIDADE NORMAL

   Um produto "pack" referencia um produto pai (`parentId`) e um
   `conversionFactor` (quantas unidades do pai compõem 1 pacote). O
   estoque de um pack é SEMPRE virtual/derivado: nunca há campo `stock`
   próprio consultado — o disponível é sempre
   `floor(estoque_disponível_do_pai / conversionFactor)`.

   Ao vender um item cujo produto original é "pack", o sistema NÃO debita o
   próprio pack — debita o produto PAI em `quantidade_vendida ×
   conversionFactor` unidades. Produtos comuns têm o próprio `stock`
   debitado diretamente.

   Cálculo de custo no carrinho: para itens pack, assume-se que o campo de
   custo do próprio pack já representa o custo total do pacote (não
   multiplica pelo fator de conversão).

5.4 GRUPOS DE PREÇO / MODO DE PRECIFICAÇÃO (Varejo, Cartão, Atacado)

   Três modos selecionáveis globalmente (`pricingMode`): Varejo (retail),
   Cartão (card), Atacado (wholesale). Trocar o modo RECALCULA o preço de
   TODOS os itens já no carrinho, não só dos próximos.

   Regra de resolução de preço:
   - Modo "wholesale" E `wholesalePrice > 0` cadastrado → usa preço de
     atacado, rótulo "ATACADO", marca `isWholesale: true`.
   - Senão, modo "card" E `cardPrice > 0` cadastrado → usa preço de
     cartão, rótulo "CARTÃO".
   - Caso contrário (inclui "retail", ou fallback quando o preço do modo
     escolhido não está cadastrado/é ≤0) → usa preço de varejo, rótulo
     "VAREJO". Ou seja, há fallback automático para o preço de varejo
     sempre que o produto não tem preço configurado para o modo
     selecionado.

   Alternância individual por item: cada linha do carrinho tem um checkbox
   "Atacado" que sobrepõe o modo global só para aquele item — habilitado
   apenas se o produto tiver `wholesalePrice > 0` cadastrado. Modo Atacado
   só é relevante se `storeConfig.enableWholesale` estiver ligado.

   Edição manual de preço por item: cada linha permite digitar um preço
   customizado, sobrescrevendo o calculado (validado como número ao perder
   o foco, com fallback para 0 se inválido) — é o único mecanismo
   equivalente a "desconto" no PDV; não há campo de desconto percentual/
   fixo dedicado, nem log de motivo de alteração de preço.

5.5 DOSES E COMANDAS (delegados a componentes dedicados)

   F9 abre o painel de Doses (`DoseManager`, ver seção 15), substituindo
   completamente o PDV enquanto aberto. Dose adicionada de volta ao
   carrinho soma quantidade se já existir item da mesma garrafa
   (`bottleId`), senão cria nova linha marcada `isDose: true` — usada
   depois para pular a pergunta de emissão de nota fiscal (vendas de dose
   só imprimem cupom automaticamente).

   F8 abre o painel de Comandas (`ComandaManager`, ver seção 16), mesma
   lógica de substituição de tela. Ao "enviar para o caixa" a partir de uma
   comanda, os itens são anexados ao carrinho atual (concatenados),
   carregando metadados de origem (`source: "tab"`, `tabId`, `tabItemId`)
   usados depois para dar baixa apenas nesses itens no documento da
   comanda após a venda (comanda esvaziada é excluída; com itens restantes,
   é atualizada).

5.6 FORMAS DE PAGAMENTO E PAGAMENTO PARTICIONADO (MULTI-PAGAMENTO)

   Formas suportadas: Dinheiro (F1), Pix (F2), Débito (F3), Crédito (F4),
   Fiado (F5), e "PERCA" (F6 — não é forma de pagamento, é registro de
   perda, ver 5.9).

   O pagamento é construído como uma lista de "entradas" (`paymentEntries`),
   cada uma com método, valor e metadados (parcelas, cliente/fiado, taxa).
   `remaining` = total do carrinho − soma já paga.

   Primeiro atalho de forma de pagamento pressionado abre o modal e
   pré-seleciona aquele método com valor sugerido = total do carrinho
   (pagamento único rápido). Com o modal já aberto, outro atalho apenas
   TROCA o método da entrada sendo digitada, sem resetar entradas já
   confirmadas — permite montar pagamento composto.

   "+ Adicionar" entrada valida: valor numérico > 0; método selecionado;
   valor não pode exceder o restante (`min(digitado, remaining)`); se
   método = Fiado, exige vencimento e cliente (novo — cria localmente com
   `debt` inicial — ou existente, selecionado da lista); se
   Crédito/Débito/Pix e houver perfis de taxa cadastrados, calcula a taxa
   sobre o valor da entrada (débito/Pix usam taxa fixa do perfil; crédito
   usa taxa por número de parcelas). Cada entrada confirmada é anexada à
   lista; o próximo valor sugerido é pré-preenchido com o restante.

   Navegação por teclado no seletor de método (setas esquerda/direita +
   Enter/Espaço); foco automático no campo de valor a cada mudança de
   método/abertura/adição/remoção de entrada.

   Revisão só liberada quando `remaining ≤ 0.005` (tolerância de
   arredondamento) e há ao menos 1 entrada.

   Determinação do "método principal" salvo na venda: o da entrada com
   MAIOR valor entre as adicionadas. `fee` total = soma das taxas de todas
   as entradas. `net` = total − taxas. `profit` = total − taxas − custo
   total dos itens. Parcelas da venda = as da entrada dominante (só se o
   método dominante for Crédito, senão 1).

   Cálculo de impostos por item: busca o produto original e seu perfil
   tributário (`taxProfileId`), chama `calculateItemTaxes` (lógica em
   `TaxCalculator.js`, ver seção 7.1) e anexa o resultado a cada item antes
   de salvar a venda.

   Cálculo de troco: NÃO EXISTE um campo/cálculo explícito de troco — o
   fluxo é orientado a "valor atribuído por forma de pagamento" (limitado
   ao restante a cobrir), não a "valor recebido menos total".

5.7 VENDA FIADO (A CRÉDITO) E CONTAS A RECEBER

   No PDV, Fiado é só mais uma forma de pagamento dentro do fluxo
   multi-pagamento, exigindo cliente e vencimento. A decisão do que fazer
   com a venda ocorre fora do PDV (`handleNewSale`/`handleNewFiadoSale`,
   ver seção 6 e 19): se a venda é ≥99% paga via Fiado, é desviada
   inteiramente para o fluxo de Contas a Receber — cria título em
   `receivables`, reserva estoque (`reserved_stock`, sem baixar o `stock`
   físico), e NÃO gera venda em `sales` nem lançamento financeiro naquele
   momento (só na quitação futura, ver seção 19).

5.8 DESCONTO — não há mecanismo dedicado; o único equivalente é a edição
    manual do preço unitário por linha (ver 5.4), sem validação de limite
    mínimo nem log de motivo.

5.9 PERDA ("PERCA" / isLoss) — F6

   Modo dedicado do modal de pagamento: mostra "Custo do Prejuízo" (soma do
   custo dos itens no carrinho) e exige motivo obrigatório (`lossReason`)
   antes de permitir revisar. Ao revisar, monta a venda com `total: 0`,
   `fee: 0`, `net: 0`, `profit: -custoTotal` (prejuízo = custo total dos
   itens perdidos), `paymentMethod: "PERCA"`, `clientName: "PERCA INTERNA"`,
   `isLoss: true`, `lossReason`.

   No fechamento (fora do PDV): dá baixa de estoque normalmente (mesma
   lógica pack/unidade), mas NÃO gera lançamento financeiro e é EXCLUÍDA
   do total de vendas do fechamento de caixa (filtrada explicitamente).
   Aparece destacada em vermelho no histórico do PDV, sem opção de
   reimpressão de cupom.

5.10 EMISSÃO DE NOTA FISCAL (disparo a partir do PDV)

   O PDV apenas finaliza a venda localmente e delega a `handleNewSale`
   (seção 6). Após venda bem-sucedida (não-perda, sem itens de dose,
   usuário caixa ou admin), abre modal perguntando se deseja emitir a nota
   fiscal agora. Vendas com itens de dose pulam essa pergunta e só imprimem
   cupom. Verificações prévias de certificado expirado (BrasilNFe) ou Bling
   desconectado, se detectadas, cancelam a tentativa automaticamente e
   imprimem apenas um "Cupom Não Fiscal" com aviso ao operador (lógica
   plena descrita na seção 6/7).

5.11 REIMPRESSÃO DE CUPOM

   Modal "Histórico Recente (6h)": lista vendas das últimas 6 horas (todas,
   se admin; só as próprias, se não-admin). Cada venda não-perda tem botão
   de reimpressão que chama a mesma função de impressão de cupom usada na
   venda original. Vendas de perda não têm essa opção.

5.12 VALIDAÇÃO DE ESTOQUE INSUFICIENTE E PERMISSÃO can_sell_without_stock

   Regra central aplicada em todos os pontos de alteração de carrinho
   (adicionar produto novo, incrementar quantidade): se estoque disponível
   < quantidade desejada, bloqueia a menos que o usuário logado tenha
   `can_sell_without_stock === true`, caso em que permite com aviso
   explícito de exceção. É um atributo do USUÁRIO (não da loja nem do
   produto), controlando estoque negativo por operador.

5.13 SANGRIA DE CAIXA — F7

   Retirada de dinheiro físico durante o expediente sem fechar a sessão.
   Exige: valor, motivo/destino (texto livre) e SENHA de autorização
   — validada contra a senha do usuário logado OU uma senha mestra fixa
   "admin123" hardcoded como fallback. Proteção contra duplo clique.

   Ao confirmar: registra a movimentação (`CaixaService.addMovement`, tipo
   EXPENSE, categoria SANGRIA, forma DINHEIRO, vinculada à sessão aberta —
   erro se não houver sessão). Busca o roteamento financeiro para
   identificar a conta bancária que representa "dinheiro"; se configurada,
   grava saída em `account_transactions` e decrementa o saldo da conta —
   refletindo a saída física de dinheiro no extrato/consolidado.

5.14 ATALHOS DE TECLADO (mapa funcional completo)

   F1–F5: inicia/alterna pagamento por Dinheiro, Pix, Débito, Crédito,
   Fiado. F6: inicia registro de Perda. F7: abre Sangria. F8: abre/fecha
   Comandas. F9: abre/fecha Doses. F10: abre fechamento de caixa (se sessão
   aberta) ou abertura (se não). F12: alterna foco/limpeza da busca. Teclas
   F1–F12 têm o comportamento nativo do navegador bloqueado.

   Dentro do modal de pagamento (etapa de confirmação): setas
   esquerda/direita alternam "Voltar"/"Fechar Venda"; Enter ativa a opção
   focada. Etapa de configuração: Enter finaliza a revisão automaticamente
   se o pagamento já estiver totalmente coberto.

   Navegação do carrinho por teclado (sem modal aberto, fora de campos de
   texto, sem dropdown de busca visível): seta baixo/cima move seleção
   entre itens; seta direita/esquerda incrementa/decrementa quantidade do
   item selecionado; Delete remove o item selecionado.

   Atalhos de forma de pagamento funcionam mesmo com foco em campo de
   texto quando o modal já está aberto na etapa de configuração.

6. STOREAPP — CASCA PRINCIPAL, NAVEGAÇÃO E ORQUESTRAÇÃO DE VENDAS
================================================================================

Componente exibido após o login, mantém o estado operacional global da loja
ativa e concentra toda a lógica compartilhada entre módulos (gravação de
vendas, emissão fiscal, verificações diárias).

6.1 NAVEGAÇÃO LATERAL E CONTROLE DE ACESSO POR MÓDULO

   Módulos existentes: Dashboard, PDV & Vendas, Estoque, Parceiros, Entradas
   & Contas, Financeiro, Precificação, Configurações — cada um só aparece se
   `canAccess(moduleId)` retornar verdadeiro (regra completa na seção 18).
   Se o usuário tenta acessar (via estado interno) um módulo sem permissão,
   é exibida a tela de "Acesso Negado" com opção de voltar ao PDV — o
   bloqueio ocorre na renderização do conteúdo, não na navegação em si.

6.2 CARREGAMENTO DE DADOS-BASE AO ENTRAR NA LOJA

   - Provedor fiscal ativo (`nfeProvider`): lido de `fiscal_provider_settings`
     (Supabase); padrão "bling" se ausente ou erro.
   - Clientes de venda: lista completa de `fiscal_clients` (Supabase),
     recarregada a cada troca de loja ou de módulo ativo — mantida fora do
     objeto global da loja para evitar cache de excluídos.
   - Usuários da loja: assinatura em tempo real da coleção `users` (base
     admin) filtrada por `storeId`.
   - Permissões de módulo: carregadas uma vez de `module_permissions`.
   - Listeners em tempo real para: `products`, `bank_accounts`, `sales`,
     `financial_movements`, `transaction_categories`.

6.3 handleNewSale — GRAVAÇÃO DE UMA VENDA

   1. Desvio para fiado: se a forma de pagamento é "Fiado" (ou cobre ≥99%
      do total em vendas multi-forma), desvia inteiramente para
      `handleNewFiadoSale` (seção 6.4) e interrompe o fluxo normal.
   2. Checagem de provedor fiscal ANTES de gravar (ver seção 7 para
      detalhes completos): se BrasilNFe e certificado expirado, ou se
      Bling e desconectado, marca a venda com status de contingência
      apropriado, avisa o usuário, imprime cupom não fiscal e INTERROMPE o
      fluxo de gravação (a venda não chega a ser persistida neste ramo).
   3. Gera ID da venda, monta objeto final com timestamp de servidor,
      usuário responsável.
   4. Sanitiza o payload recursivamente (substitui qualquer `undefined` por
      string vazia, preservando objetos nativos do Firebase) — evita falhas
      de gravação por campos indefinidos de comandas/carrinho incompletos.
   5. Baixa de estoque (dentro do mesmo lote atômico): produto pack debita
      o produto pai em `qty × conversionFactor`; produto normal debita o
      próprio estoque. Itens de comanda são agrupados para processamento
      posterior.
   6. Lançamento financeiro automático (se a venda NÃO for perda): cria
      registro em `financial_movements` (INCOME, categoria "Vendas");
      busca o roteamento de forma de pagamento → conta bancária em
      `financial_settings/routing`; para cada forma de pagamento roteada
      (suporta múltiplas formas na mesma venda, excluindo Fiado), grava
      entrada em `account_transactions` (valor líquido de taxa) e
      incrementa o saldo da conta correspondente. Sem conta configurada
      para a forma, nenhum lançamento bancário é feito (só o
      `financial_movements` genérico permanece).
   7. Commit atômico de tudo acima em um único lote.
   8. Baixa de comandas (pós-commit): para cada comanda com itens vendidos,
      remove os itens vendidos; se ficar vazia, o documento é excluído,
      senão é atualizado com os itens remanescentes.
   9. Decisão pós-venda: itens de dose → imprime cupom automaticamente e
      notifica, sem perguntar sobre nota fiscal; venda elegível (não-perda,
      sem dose, usuário caixa/admin) → abre modal perguntando sobre
      emissão de NF-e/NFC-e; demais casos → apenas notifica sucesso.
   10. Qualquer exceção é capturada, logada e notificada como erro
       genérico.

6.4 handleNewFiadoSale — ver detalhamento completo na seção 19 (Contas a
    Receber).

6.5 handleFinalizeFiadoSale — ver detalhamento completo na seção 19.

6.6 ALTERNÂNCIA ENTRE PROVEDORES FISCAIS — ver seção 7 (detalhamento
    completo do mecanismo e dos dois fluxos de emissão).

6.7 MODAL DE DECISÃO PÓS-VENDA (emissão de NF-e / cupom não fiscal)

   Passo 1 — "Deseja emitir a Nota Fiscal (NFC-e) agora?": "Não Emitir"
   avança direto ao passo 2; "SIM, EMITIR" dispara a emissão (roteada para
   Bling ou BrasilNFe conforme configuração) e também avança ao passo 2.

   Passo 2 — "Deseja imprimir o cupom não fiscal da venda?": "Não Imprimir"
   fecha o modal; "Imprimir" chama a impressão de cupom térmico; botão
   "Voltar" retorna ao passo 1.

   Navegação por teclado: setas esquerda/direita alternam foco entre os
   dois botões de cada passo; Enter confirma a opção focada.

6.8 VERIFICAÇÕES DIÁRIAS AUTOMÁTICAS — detalhadas na seção 7.4.

6.9 NOTIFICAÇÃO DE CONTAS A PAGAR PRÓXIMAS DO VENCIMENTO

   Executa 2 segundos após carregar a loja, limitada a uma vez por dia.
   Consulta notas de entrada não canceladas; para cada parcela pendente,
   calcula dias restantes até o vencimento. Se faltarem exatamente 5 dias
   (e ainda não avisado para aquela parcela): aviso individual "Conta vence
   em 5 dias: {fornecedor}". Conta quantas parcelas vencem em até 3 dias
   ("urgentes"); se houver ao menos uma e ainda não avisado hoje: alerta
   consolidado "ATENÇÃO: Existem N contas vencendo em breve!" (severidade
   erro).

6.10 IMPRESSÃO DE CUPOM NÃO FISCAL / REIMPRESSÃO (printReceipt)

   Monta um recibo em texto monoespaçado (nome/endereço/CNPJ da empresa,
   cabeçalho "CUPOM NAO FISCAL", data/hora, cliente, itens com quantidade e
   valores, total, forma de pagamento com parcelas se houver, mensagem de
   agradecimento), renderiza em iframe oculto formatado para impressora
   térmica de 80mm e aciona a impressão do navegador.

   Pontos de uso: bloqueio de venda por certificado expirado/Bling
   desconectado; vendas de dose; modal de decisão pós-venda; reimpressão a
   partir do módulo Financeiro (histórico de vendas, qualquer venda já
   registrada pode ser reimpressa a qualquer momento, reutilizando o mesmo
   formato do cupom original).

6.11 SESSÃO DE CAIXA — o StoreApp não abre/fecha sessões diretamente; apenas
     referencia `sessionId` ao registrar vendas fiado. Toda a experiência
     de abertura/fechamento vive no PDV (seção 5.1) e no `CaixaService`
     (seção 14).

6.12 INTEGRAÇÃO COM MÓDULOS FILHOS — o StoreApp conecta cada módulo às
     fontes de dados corretas e callbacks centrais: Dashboard (vendas em
     tempo real, navegação para recebível específico), PDV (produtos,
     grupos de preço, clientes, perfis de taxa, callback de nova venda e
     de atualização em lote de produtos), Transactions/Entradas & Contas
     (callback de finalizar fiado), Finance (callback de impressão e de
     emissão de nota — permite emitir retroativamente a partir da tela
     financeira), InventoryWMS (produtos, vendas, clientes como
     "fornecedores"), SettingsManager (usuários, dados da empresa,
     persistência via atualização do documento global da loja).

7. EMISSÃO FISCAL (NF-e/NFC-e) — PROVEDORES BLING E BRASILNFE
================================================================================

O sistema suporta DOIS provedores de emissão fiscal coexistentes, escolhidos
por loja pelo Super Admin (seção 3.7). Historicamente o sistema usava apenas
a BrasilNFe; a integração com o Bling foi adicionada depois como alternativa,
e a BrasilNFe foi restaurada/mantida em paralelo para permitir rollback
imediato por loja em caso de instabilidade de qualquer um dos dois provedores
— por isso os dois fluxos completos convivem no código, nunca acionados
simultaneamente para a mesma loja.

7.1 CÁLCULO DE IMPOSTOS (comum aos dois provedores — `TaxCalculator.js`)

   Função `calculateItemTaxes(produto, cliente, dadosDaEmpresa, perfilFiscal)`
   usada tanto no PDV (ao montar a venda) quanto nos dois fluxos de emissão
   (ao recalcular impostos "frescos" no momento de emitir). A partir do
   perfil tributário vinculado ao produto (CSOSN, CFOP, origem, CST
   PIS/COFINS e alíquotas — ver seção 17), monta os valores de ICMS, PIS e
   COFINS aplicáveis àquele item, incluindo a lógica de produto monofásico
   (CST 04 → PIS/COFINS com alíquota zero, repassado já recolhido pelo
   fabricante).

7.2 PROVEDOR "BLING"

   7.2.1 Configuração (`BlingIntegrationPanel`, acessível só pelo Super
   Admin dentro do modal de gestão da loja — seção 3.7):
   - Credenciais OAuth do aplicativo cadastrado no Bling: Client ID e
     Client Secret, mais o link de redirecionamento fixo (raiz do domínio
     do sistema) que deve ser cadastrado no lado do Bling.
   - Fluxo de conexão: ao clicar em "Conectar com Bling", gera um `state`
     aleatório anti-CSRF, salva no `sessionStorage` (junto com o ID da loja
     sendo configurada) e redireciona o navegador para a tela de
     autorização do Bling.
   - Referências obrigatórias para emitir: Natureza de Operação (uma para
     NF-e, outra para NFC-e) e mapeamento de Forma de Pagamento (Dinheiro,
     Crédito, Débito, Pix, Outros) para os IDs correspondentes cadastrados
     no Bling — podem ser carregadas automaticamente do Bling (botão
     "Carregar do Bling", preenchendo selects) ou digitadas manualmente.
   - Desconectar: revoga os tokens junto ao Bling (melhor esforço) e limpa
     `access_token`/`refresh_token`/`connected` no registro da loja.

   7.2.2 Callback OAuth (nível raiz do `App`): o Bling redireciona de volta
   à raiz do sistema com `?code=&state=` na URL, recarregando toda a SPA.
   O sistema detecta os parâmetros, limpa a URL imediatamente, recupera o
   `state`/`storeId` salvos no `sessionStorage` (uso único, removidos após
   ler), valida que o `state` retornado bate exatamente com o salvo (
   proteção anti-CSRF — se não bater ou faltar `storeId`, mostra erro e
   aborta). Se válido: troca o `code` por tokens de acesso junto ao Bling,
   calcula a expiração, salva `access_token`/`refresh_token`/
   `token_expires_at`/`connected: true`/`connected_at` no registro da loja,
   e grava a chave `bling_reopen_store_id` no `sessionStorage` para que o
   painel do Super Admin reabra automaticamente a gestão daquela loja
   assim que a página recarregar. Todo esse processo é automático, sem
   ação manual adicional do usuário além do clique inicial em "Conectar".

   7.2.3 Renovação automática de token: antes de qualquer chamada à API do
   Bling, o sistema garante um token válido — se estiver expirado ou
   expirando em menos de 60 segundos, renova usando o `refresh_token` e
   persiste os novos tokens.

   7.2.4 Emissão de venda via Bling (`handleEmitNFeBling`):
   - Verifica conexão ativa; obtém dados completos do cliente (se houver).
   - Decide o modelo: NFC-e (65, padrão) ou NF-e (55) — regra: se o
     documento do cliente tem mais de 11 dígitos (pessoa jurídica) OU o
     cliente tem endereço completo (CEP e logradouro preenchidos), emite
     NF-e; caso contrário, NFC-e.
   - Recalcula impostos de cada item com o perfil tributário mais recente.
   - Monta o payload da nota (natureza de operação, forma de pagamento,
     itens) e envia para criação no Bling, depois solicita o envio à SEFAZ.
   - Aguarda confirmação via polling: até 8 tentativas, 2,5s de intervalo;
     situações finais: autorizada, rejeitada ou denegada.
   - Sem confirmação dentro das tentativas: marca a venda como
     "PROCESSANDO" e avisa que a confirmação está demorando (consultar
     depois em Notas Fiscais Emitidas).
   - Autorizada: grava registro completo em `fiscal_invoices` (Supabase) —
     ambiente, modelo, ID da nota no Bling, número, série, chave, status,
     links de DANFE/PDF, XML em base64, cliente, valor. Dispara best-effort
     (não bloqueia, só loga aviso em falha) o lançamento automático de
     contas e estoque dentro do próprio Bling. Atualiza a venda com status
     autorizado e notifica com o número da nota.
   - Rejeitada/Denegada: mensagem específica por situação, atualiza a venda
     com status de rejeição e notifica o operador.

   7.2.5 Cancelamento e Carta de Correção (a partir da tela de Notas
   Fiscais Emitidas — seção 10): CANCELAR é suportado (chama a API do
   Bling com a justificativa); CARTA DE CORREÇÃO NÃO é suportada para
   notas Bling — o sistema bloqueia explicitamente essa ação com mensagem
   informando a limitação (o botão de correção só aparece para notas do
   provedor BrasilNFe legado).

7.3 PROVEDOR "BRASILNFE" (LEGADO)

   7.3.1 Configuração (aba "Certificado (BrasilNFe)" em Configurações da
   própria loja — seção 9, não restrita ao Super Admin):
   - Upload do Certificado Digital A1 (.pfx/.p12), convertido para base64
     no navegador.
   - Ambiente de Emissão: Homologação (Teste) ou Produção.
   - Senha do Certificado.
   - CSC ID e Código CSC (obrigatórios para emitir NFC-e).
   - Verificação local do certificado (client-side, biblioteca `forge`):
     sempre que há base64+senha disponíveis, tenta decodificar a estrutura
     PKCS#12 e extrair validade e titular do certificado, exibindo card de
     status (válido/expirado) — verificação puramente informativa, não
     confirma validade perante a SEFAZ.
   - Ao salvar: se um novo certificado foi carregado nesta sessão, primeiro
     reenvia o arquivo à API BrasilNFe; depois grava/atualiza (upsert por
     loja) o registro completo em `fiscal_settings` (Supabase).

   7.3.2 Emissão de venda via BrasilNFe (`handleEmitNFeBrasilNFe`):
   - Verifica token de API configurado.
   - Mesma regra de decisão de modelo NF-e/NFC-e do Bling (documento com
     mais de 11 dígitos ou endereço completo → NF-e; senão NFC-e).
   - CÁLCULO MANUAL DE NUMERAÇÃO SEQUENCIAL (diferença chave frente ao
     Bling, que numera pelo próprio provedor): busca no Supabase a última
     nota emitida daquele modelo e ambiente para a loja (produção e
     homologação nunca se misturam na numeração) e calcula
     `próximo = última + 1` (ou 1 se não houver nenhuma).
   - Recalcula impostos dos itens (usando perfil se encontrado, ou cálculo
     básico sem perfil).
   - Monta o payload com o número calculado; valida ambiente ("1" produção
     ou "2" homologação, senão erro).
   - Envia diretamente à API BrasilNFe (chamada síncrona, sem polling —
     resposta imediata).
   - Autorizada: grava registro completo em `fiscal_invoices` (número,
     série, chave, protocolo, status, PDF em base64, XML), atualiza a
     venda, notifica com o número da nota.
   - Rejeitada: extrai mensagem de erro da resposta da API, atualiza a
     venda com status de rejeição e notifica.

   7.3.3 Cancelamento e Carta de Correção (Notas Fiscais Emitidas):
   - CANCELAR: detecta o protocolo pela `nfe_protocol` salva; se ausente,
     tenta extrair do próprio XML salvo via regex sobre a tag `<nProt>`
     (fallback de recuperação de dados legados); se mesmo assim não achar
     protocolo, bloqueia a ação com mensagem específica. Envia cancelamento
     à API BrasilNFe com chave, protocolo e justificativa.
   - CARTA DE CORREÇÃO (CC-e): exclusiva deste provedor; envia texto de
     correção à API, e marca a nota como "com correção" em caso de sucesso.

7.4 ALTERNÂNCIA DE PROVEDOR E VERIFICAÇÕES QUE DEPENDEM DELA

   O valor `nfeProvider`, lido de `fiscal_provider_settings` ao carregar a
   loja (padrão "bling" se ausente), governa três pontos do sistema:
   1. Checagem prévia ao gravar uma venda (seção 6.3, passo 2): decide
      entre validar certificado digital (BrasilNFe) ou conexão Bling.
   2. Emissão da nota: roteador `handleEmitNFe` decide entre
      `handleEmitNFeBrasilNFe` e `handleEmitNFeBling`.
   3. Verificação diária automática (uma vez por dia por loja, 3,5s após
      carregar):
      - BrasilNFe: decodifica o certificado salvo e calcula dias até
        expirar — 1 a 7 dias restantes → aviso de atenção; vencido → aviso
        crítico "Emissão bloqueada" (o bloqueio efetivo ocorre em
        `handleNewSale`, seção 6.3); tudo certo → não avisa, mas marca
        como checado no dia.
      - Bling: consulta `connected`/`refresh_token`; se ausente/desconecta-
        do, avisa que a integração não está conectada e a emissão está
        indisponível.

   Fluxo de confirmação legado (`handleConfirmEmission`, associado a um
   modal de pré-visualização de payload que não é acionado por nenhum botão
   ativo no fluxo atual — código mantido por compatibilidade): também
   branch por provedor, reenviando o mesmo payload já validado no preview
   (BrasilNFe) ou criando+enviando a nota ao Bling a partir do preview.

7.5 MANUTENÇÃO (`MaintenancePanel`, restrito ao Super Admin — seção 3.7)

   Duas ferramentas destrutivas e permanentes, por loja:
   - Reset de Dados do Dashboard: seleção por checkbox das coleções a
     apagar permanentemente entre Vendas, Despesas/Receitas Lançadas,
     Extrato das Contas Bancárias, Sessões de Caixa, Movimentações de
     Caixa (Sangrias), Histórico de Fechamentos de Caixa, Notas Fiscais
     Emitidas — Produtos e Comandas NUNCA aparecem nesta lista
     (propositalmente protegidos, nunca excluíveis por aqui). Exige digitar
     "RESETAR" para habilitar o botão. Apaga em lotes de 450 documentos por
     vez (limite de 500 operações por lote do Firestore).
   - Zerar Quantidade em Estoque: zera apenas o campo de estoque de todos
     os produtos da loja, mantendo o cadastro (nome, preço, NCM, código de
     barras etc.) intacto.

8. FINANCEIRO (Fechamento de Caixa, Relatórios, Configuração de Taxas)
================================================================================

Módulo orquestrador (`Finance`) com 7 abas/telas.

8.1 CONFIGURAÇÃO DE TAXAS ("Config. Taxas" — `FinanceSettings`)

   Cadastro de "Perfis de Taxa" (custo cobrado pela adquirente/maquininha):
   nome do perfil, taxa de Débito (%), taxa de Pix (%), e uma taxa de
   Crédito Parcelado independente para cada quantidade de parcela de 1x a
   12x. Único campo obrigatório para salvar: Nome (senão bloqueia com
   erro). Perfil salvo em memória local (repassado via props — a
   persistência real, se houver, fica fora deste componente). Exclusão de
   perfil sem confirmação, direta da lista.

8.2 HISTÓRICO DE DESPESAS (`ExpenseHistory`)

   Lista despesas (`financial_movements` tipo EXPENSE) com filtros de
   período (padrão: mês corrente) e categoria. Total do período em
   destaque. Cada linha mostra classificação Operacional/Outros (derivada
   da categoria — categoria ausente/excluída é tratada como Operacional
   por padrão) e status (Pago/Pendente).

   Exclusão de despesa: pede confirmação; apaga o lançamento em
   `financial_movements`; se a despesa tinha conta bancária vinculada,
   localiza o lançamento correspondente em `account_transactions` (por
   conta+valor+data+descrição) e também o remove, REVERTENDO o saldo da
   conta bancária (`increment` do valor de volta) — mantém consistência
   entre extrato e despesas ao desfazer.

8.3 FECHAMENTO DE CAIXA / DRE DIÁRIO (`CashClosure`)

   Painel de resultado (DRE simplificado) do período corrente, comparando
   o esperado contra o efetivamente creditado no banco:
   - Venda Bruta: soma de vendas não-perda.
   - CMV: soma por item (`custo × quantidade`) quando a venda tem itens
     detalhados; fallback ao campo agregado de custo em vendas antigas sem
     detalhamento.
   - Taxas: percentual do perfil de taxa aplicável à forma de pagamento de
     cada venda.
   - Despesas pagas do período, separadas em Operacionais e Outras
     (conforme a categoria); Sangrias somadas à parte (NÃO entram no
     cálculo de lucro líquido — são apenas transferência de caixa, não
     despesa real).
   - Perdas: custo das vendas marcadas `isLoss`.
   - Lucro Líquido = Venda Bruta − CMV − Taxas − Operacional − Outras −
     Perdas.
   - Auditoria "PDV vs Banco": compara o líquido esperado (bruto menos
     taxas) contra o que de fato entrou no banco como venda; tolerância de
     10 centavos para considerar "conferido". PURAMENTE INFORMATIVO — o
     botão "Fechar Caixa do Dia" funciona independentemente do resultado
     da auditoria, sem bloqueio nem confirmação extra em caso de
     divergência.
   - Bloco de barras proporcionais (Faturamento, CMV, Taxas, Despesas
     Operacionais, Perdas, Outras Despesas, Lucro Líquido).
   - "Fechar Caixa do Dia" apenas grava o resumo num array local em
     memória — não persiste em nenhuma coleção do banco (perdido ao
     recarregar a página; ver Apêndice A).

8.4 RELATÓRIO FINANCEIRO MENSAL (`FinancialReport`) — DRE completo

   Filtros: mês, ano (lista fixa 2024–2026), operador específico ou todos.
   Cálculo do DRE: Receita (vendas válidas), CMV (por item, contornando um
   bug conhecido de cálculo agregado em produtos "pack"), Taxas (lidas do
   campo já gravado na venda, fonte diferente do `CashClosure`), Perdas,
   Despesas por categoria, Lucro Bruto, Lucro Líquido, Margem Líquida,
   Ticket Médio.

   Diagnóstico de CMV suspeito: se o CMV do período ultrapassar 150% da
   receita, exibe painel de alerta com os 8 produtos que mais pesaram no
   custo, destacando em vermelho os com custo unitário acima de R$500 como
   possivelmente incorretos — puramente diagnóstico, não altera valores.

   Card "Posição de Estoque": valor total em estoque HOJE (não é histórico
   do mês filtrado).

   Exportações: PDF (captura visual da tela), Excel/XLS (tabela do DRE),
   SPED simplificado (arquivo texto — inclui apenas vendas com nota
   autorizada; modelo de documento fixado em "55" independente do modelo
   real da nota; maior parte dos campos tributários zerados — não é um SPED
   fiscalmente completo, é um esqueleto simplificado).

8.5 VENDAS (LISTA) — histórico completo com filtros de data/cliente/forma
    de pagamento; badges de status (NF-e OK, Rejeitada, Fiado, Perca,
    Pago); ações por linha: ver detalhes, reimprimir cupom, baixar PDF da
    nota autorizada (consulta `fiscal_invoices`), emitir NFC-e/NF-e
    (retroativamente, se ainda não autorizada) com rótulo "Reemitir" quando
    rejeitada. Vendas de perda nunca mostram botões de emissão fiscal.

8.6 RELATÓRIO MENSAL — ver 8.4.

8.7 CONFIG. TAXAS — ver 8.1.

8.8 HISTÓRICO DE FECHAMENTOS — lista os fechamentos feitos na sessão atual
    (ver 8.3, não persistido em banco).

8.9 CONTAS BANCÁRIAS / CONCILIAÇÃO — sub-abas que delegam aos componentes
    `BankAccountsManager` (seção 13) e `CashClosingManager` (seção 14).

8.10 RELATÓRIOS DE CAIXA — auditoria histórica, SOMENTE LEITURA, de
     sessões de caixa (abertura/fechamento por operador), distinta do DRE
     acima: filtros de período e caixa; controle de acesso (não-admin só
     vê as próprias sessões); tabela com operador, horários, total de
     vendas, retirada, saldo residual, status; linha expansível mostra
     resumo financeiro completo da sessão, destino da retirada (conta ou
     "Outros") e observação registrada no fechamento.

10. ENTRADA DE NOTAS, CONTAS A PAGAR, NOTAS FISCAIS EMITIDAS, TRANSAÇÕES
================================================================================

10.1 ENTRADA DE NOTA FISCAL DE COMPRA (`EntradaNotas.js`)

   Wizard de 3 passos (Cabeçalho → Itens → Financeiro), com dois modos:
   importação de XML de NF-e/NFC-e ou digitação manual.

   Tipos de Movimento fixos (não configuráveis pela tela), cada um
   definindo o comportamento de estoque e financeiro da nota:
   - 101 Compra Mercadoria p/ Revenda: entrada → soma estoque, gera Contas
     a Pagar.
   - 102 Compra Bonificada: entrada → soma estoque, sem ação financeira.
   - 301 Venda Distribuição: saída → subtrai estoque, deveria gerar Contas
     a Receber (ver lacuna no Apêndice A).
   - 501 Lançamento de Despesas/Serviços: saída → neutro no estoque, gera
     Contas a Pagar.

   Passo 1 — Cabeçalho: estabelecimento, tipo de operação (obrigatório),
   série, número (obrigatório), datas, chave de acesso (só no modo XML),
   observações, condição/forma de pagamento. Busca de parceiro
   (fornecedor/cliente) incremental em `fiscal_clients`; cadastro rápido de
   novo fornecedor com autopreenchimento de endereço via CEP.

   Importação de XML: exige tipo de operação já selecionado. Extrai número
   da nota, dados do parceiro (emitente ou destinatário, conforme a
   direção do movimento escolhido), itens (quantidade, valor, código,
   descrição, NCM, EAN, unidade, CFOP) e parcelas de cobrança (`cobr/dup`).
   Casamento de item com produto cadastrado por hierarquia de prioridade:
   código de barras exato não-pack > código de barras exato qualquer tipo >
   SKU interno exato não-pack > SKU interno exato qualquer tipo — evita
   confundir "caixa" com "unidade" quando compartilham código. Sem
   correspondência por código, tenta por nome exato. Item sem
   correspondência fica pendente e pode ser criado automaticamente como
   novo produto ao salvar.

   Grid de itens: recálculo automático de total/preço/margem ao editar
   quantidade, custo, margem ou preço de venda (trava opcional "Recalcular
   Venda ao alterar Custo?"); busca e vínculo de código de barras/SKU com
   nova sugestão em tempo real; vínculo de embalagem/pack (item "pai" tipo
   caixa) com criação rápida de produto unitário filho ou seleção de
   existente.

   Passo 3 — Financeiro: geração automática de parcelas (divisão igual do
   total, resíduo de arredondamento absorvido pela última parcela,
   vencimentos por incremento mensal), reativa a qualquer mudança de
   configuração (quantidade de parcelas, forma de pagamento, checkbox
   "Lançar como Pago").

   Salvamento (transação em lote): grava a capa da nota em `invoices`;
   gera parcelas em Contas a Pagar (só para tipos com ação financeira
   "PAGAR"); atualiza/cria produtos (produto inexistente nasce com estoque
   inicial = quantidade da nota; produto existente tem estoque incrementado
   e custo/histórico de fornecedor atualizados — preço de venda só é
   recalculado se a trava estiver ativa); cascata de pack: entrada de
   caixas também incrementa o estoque da unidade-pai na proporção do fator
   de conversão.

10.2 CONTAS A PAGAR (`AccountsPayable.js`)

   Unifica parcelas de Notas Fiscais de entrada e despesas manuais em um
   modelo comum de "parcela". Filtros: mês de referência, categoria (
   derivada dos produtos da nota, ou da própria despesa), busca textual.
   KPIs: A Pagar (Pendente+Atrasado) e Já Pago do mês filtrado.

   Dar baixa manual: seleciona conta bancária, cria lançamento em
   `account_transactions` (saída) e decrementa o saldo — SEM validar saldo
   suficiente (pode ficar negativo, diferente de Transactions.js, ver
   Apêndice A); marca a parcela/despesa como paga.

   Agendamento de pagamento automático: marca a parcela com data futura de
   efetivação e conta de saída; um "robô" reativo varre periodicamente as
   parcelas agendadas cuja data já chegou e as processa automaticamente
   (lança extrato, debita conta, marca como pago), com trava contra
   execução concorrente duplicada.

   Exclusão de documento: apaga a nota/despesa inteira sem confirmação
   aprofundada e SEM reverter estoque nem lançamentos financeiros já
   gerados (ver Apêndice A).

10.3 NOTAS FISCAIS EMITIDAS (`FiscalInvoices.js`) — ver detalhamento
    completo de ações (cancelar, carta de correção, download) na seção 7
    (comportamento distinto por provedor Bling/BrasilNFe). Filtros de
    pesquisa: cliente, modelo (55/65), intervalo de datas, status/evento
    (Autorizadas/Canceladas/Com Correção). Exclusão do registro local exige
    confirmação por SENHA do usuário logado (comparação em texto puro) —
    não cancela nada na SEFAZ/Bling, é só remoção do registro local.

10.4 TRANSAÇÕES / LANÇAMENTO MANUAL DE DESPESA (`Transactions.js`)

   Hub que organiza as abas Entrada de Notas, Contas a Pagar, Contas a
   Receber e Notas Fiscais, mais o modal global de "Lançar Despesa":
   descrição, valor (aceita vírgula decimal brasileira), data de
   competência, categoria (com criação rápida inline), conta de saída.

   Regra de status automático: data futura → PENDENTE (vai para Contas a
   Pagar, sem débito imediato, conta bancária opcional); data hoje/passada
   → PAGO (exige conta bancária selecionada).

   REGRA DE BLOQUEIO POR SALDO INSUFICIENTE: se o status calculado é PAGO,
   compara o valor da despesa com o saldo atual da conta selecionada — SE
   O SALDO FOR MENOR, A OPERAÇÃO É BLOQUEADA por completo (nada é salvo),
   com alerta explícito mostrando saldo atual vs. valor da despesa. Esta é
   a ÚNICA tela do conjunto financeiro que efetivamente impede a operação
   por saldo insuficiente (contraste com 10.2, que debita mesmo sem
   saldo).

   Se validado, grava a despesa em `financial_movements` e, apenas se PAGO
   com conta selecionada, também lança em `account_transactions` e debita
   o saldo da conta.

11. ESTOQUE (WMS), SUGESTÃO DE COMPRA E GRUPOS DE PREÇO
================================================================================

11.1 CADASTRO DE PRODUTOS (`InventoryWMS.js`)

   Campos: identificação (nome, código de barras principal + adicionais,
   categoria), tipo de item (Revenda/unit, Caixa-Fardo/pack, Suprimento/
   supply — este último com flag de habilitar no PDV), formação de preço
   (custo, margem, preço varejo, preço cartão, preço atacado), estoque
   (quantidade, mínimo, unidade), dados fiscais (NCM, CEST, perfil
   tributário vinculado), estrutura de embalagem (produto pai para packs,
   fator de conversão), fornecedor padrão e histórico completo de
   fornecedores/custos, configuração de doses (volume da garrafa, volume
   da dose, preço da dose — com cálculo em tempo real de quantas doses a
   garrafa rende).

   Cálculo automático de preço: editar Custo ou Margem recalcula o Preço
   de Venda (`custo × (1 + margem/100)`); editar Preço recalcula a Margem
   a partir do custo. Preço Cartão e Preço Atacado são independentes,
   editados livremente.

   Herança fiscal: produto sem perfil tributário próprio, mas com produto
   pai definido, herda o perfil tributário do pai ao salvar.

   Criação rápida de Caixa/Fardo vinculada à unidade: sub-formulário que
   cria simultaneamente um segundo produto tipo "pack" já vinculado
   (`parentId`), com nome sugerido, NCM herdado, quantidade/fator de
   conversão editável (recalcula custo total e preço mantendo a margem),
   margem herdada. Alternativa: vincular a uma caixa "órfã" já cadastrada
   (sem pai, ou já pertencente a este produto).

   Aba Fornecedores & Custos: busca inteligente com autocomplete em
   `fiscal_clients`; reaproveita fornecedor existente ou cria novo
   automaticamente; cada vínculo registra nome, SKU do fornecedor, último
   custo, data — vínculos duplicados (mesmo fornecedor) substituem o
   registro anterior (mantém só o "corrente" por fornecedor); tabela
   calcula variação percentual de preço frente à cotação anterior do mesmo
   fornecedor (seta vermelha/verde).

   Aba Impostos: simulação (não persistida) dos tributos que incidiriam
   sobre a venda de 1 unidade ao preço atual, usando o perfil tributário
   selecionado.

11.2 AJUSTES DE ESTOQUE MANUAIS (Movimentação Rápida)

   Entrada (+) processada direto; Saída (−) exige motivo obrigatório em
   texto livre. Regra pack: ajuste em item "pack" é sempre aplicado ao
   produto PAI multiplicado pelo fator de conversão, nunca ao próprio pack
   (que nunca guarda estoque físico).

   Baixa com motivo gera automaticamente: (1) um registro em `sales`
   simulando uma "venda" de valor zero com `isLoss: true` e o motivo, para
   rastreabilidade; (2) uma despesa já paga em `financial_movements`
   (categoria "Percas e Quebras") no valor do custo perdido.

11.3 SAÍDA AVULSA (modo de baixa em lote)

   Carrinho lateral de produtos com justificativa categorizada obrigatória
   (Devolução ao Fornecedor, Bonificação/Brinde, Consumo Interno,
   Perda/Avaria, Ajuste de Inventário, Outro). Ao confirmar (em lote): baixa
   o estoque de cada item diretamente (sem tratamento especial de
   pack/pai nesta rotina especificamente) e grava um único registro de
   auditoria em `stock_movements` com a justificativa e a lista de itens.

11.4 ESTOQUE EXIBIDO (getDisplayStock, definição local ao WMS)

   Produto pack: `floor(estoque do pai / fator de conversão)`. Produto
   normal: valor bruto do campo de estoque. Nesta implementação específica
   do WMS, esta função NÃO desconta estoque reservado por vendas fiado — a
   dedução de `reserved_stock` existe em outra implementação da mesma ideia
   usada no restante do sistema (Dashboard, PDV) — ver Apêndice A.

11.5 PAGINAÇÃO — três listagens paginadas client-side independentes
    (produtos: 50/página; produtos parados: 30/página; seleção de
    auditoria: 50/página).

11.6 EXPORTAÇÃO DE ESTOQUE EM PDF — lista completa de produtos (nome,
    código de barras, NCM), numerada.

11.7 ANÁLISE DE PRODUTOS PARADOS ("Dead Stock")

   Parâmetro ajustável: dias de inatividade (padrão 30). Produto entra na
   lista se dias desde a última venda ≥ limite (nunca vendido = 9999 dias)
   E tiver estoque positivo. Métricas: dias sem venda, "Dinheiro Parado"
   (estoque × custo), "Sugestão Promo" (preço atual × 0,85, apenas
   sugestão exibida, não aplicada).

11.8 COTAÇÃO INTELIGENTE / SUGESTÃO DE COMPRA (`PurchaseSuggestion.js`)

   Parâmetros ajustáveis: "Análise (Dias)" (janela de histórico de vendas,
   padrão 30) e "Cobertura (Meta)" (dias de estoque desejados à frente,
   padrão 15).

   Cálculo: giro diário = vendido no período / dias de análise; cobertura
   atual = estoque atual / giro diário (999 dias se nunca vendeu e estoque
   zero, para não quebrar a ordenação); se cobertura atual < meta, sugere
   `giro diário × meta − estoque atual` (arredondado para cima); se o
   estoque atual for menor que o mínimo cadastrado, a diferença até o
   mínimo prevalece se for maior que a sugestão calculada pelo giro.

   Montagem de pedido: cada produto pode ser expandido para ver as
   "Melhores Ofertas" (fornecedores do histórico, ordenados por compra mais
   recente, com custo e data); clicar adiciona/remove ao carrinho vinculado
   àquele fornecedor; quantidade editável; agrupamento automático dos
   itens do carrinho por fornecedor. Saída: cópia de texto formatado (estilo
   WhatsApp) ou exportação em PDF, um bloco por fornecedor — SEM
   integração automática com Entrada de Notas nem persistência de um
   pedido formal no banco (é sempre um artefato manual externo).

11.9 GRUPOS DE PREÇO (`PriceGroups.js`)

   Grupo = nome + margem percentual. CRUD com listener em tempo real.
   Exclusão desvincula (não apaga) os produtos do grupo, avisando que eles
   "perderão a automação".

   Associação: um produto pertence a no máximo 1 grupo por vez (campo
   único `priceGroupId`); busca e vínculo/desvínculo direto do produto.

   Preço sugerido (calculado ao vivo, não persistido) = custo × (1 +
   margem do grupo / 100). Indicador de divergência quando o preço real
   salvo no produto difere do sugerido em mais de R$0,05.

   Sincronização em Lote: recalcula e grava o preço de venda de TODOS os
   produtos do grupo aplicando a fórmula da margem — só atualiza os que
   realmente mudam mais de R$0,01 (evita writes desnecessários). A margem
   do grupo NÃO empurra o preço do produto automaticamente em tempo real —
   é preciso disparar esta sincronização manualmente após qualquer
   alteração de custo ou de margem do grupo.

12. CLIENTES E FORNECEDORES (`ClientsManager.js`)
================================================================================

Cliente e Fornecedor são o MESMO cadastro (`fiscal_clients`, Supabase);
diferenciados apenas por uma tag no array `tags` ("CLIENTE" ou
"FORNECEDOR"), definida por um checkbox no formulário.

Campos: tipo de pessoa (PF/PJ, com máscara de documento correspondente,

exclusão com confirmação.

Estatísticas/Histórico do Fornecedor (só quando marcado como fornecedor):
busca notas de compra vinculadas (por ID e, como fallback complementar, por
nome do fornecedor na nota), deduplicadas e ordenadas por data. Aba
Histórico lista as notas; aba Produtos monta a lista única de produtos já
comprados daquele fornecedor (resolvendo nome real do produto no catálogo
quando possível).

Listagem: filtro por abas (Todos/Clientes/Fornecedores) e busca textual por
nome ou documento.

13. CONTAS BANCÁRIAS (`BankAccountsManager.js`)
================================================================================

Cadastro: nome, tipo (Conta Corrente/Poupança/Caixa Físico), saldo inicial
— se maior que zero, gera automaticamente um lançamento de entrada
"SALDO INICIAL" no extrato (diferente do Reajuste de Saldo, que não deixa
rastro — ver abaixo).

Roteamento de formas de pagamento: define, para cada forma (Dinheiro, Pix,
Cartão de Crédito, Cartão de Débito, Transferência), qual conta bancária
recebe o valor — documento único `financial_settings/routing`, consumido
por praticamente todos os fluxos de venda/recebimento do sistema.

Extrato (Ledger) por conta, em tempo real: filtros por operador e por
período; duas colunas (Entradas/Saídas) com totais e "Saldo do Período".
Tratamento especial de datas `YYYY-MM-DD` como meio-dia local, evitando
deslocamento de fuso horário.

Conciliação: checkbox por transação (`reconciled`) — puramente um marcador
de acompanhamento, não afeta saldo nem totais.

Editar transação individual: recalcula automaticamente o delta de saldo da
conta (reverte o efeito antigo, aplica o novo) em uma operação atômica.

Excluir transação individual: reverte o efeito no saldo da conta
(incrementa se era saída, decrementa se era entrada), com aviso explícito
na confirmação.

Transferência entre contas: sempre gera DOIS lançamentos rastreáveis (saída
na origem, entrada no destino, referenciados entre si), mantendo a soma
total do sistema inalterada.

Reajuste de Saldo: corrige o `currentBalance` diretamente para um valor
absoluto informado, SEM gerar transferência nem lançamento algum no
extrato — uso explícito para correções pontuais (ex.: divergência de saldo
inicial); é a ÚNICA operação do módulo que altera saldo sem deixar
histórico.

14. FECHAMENTO DE CAIXA POR CALENDÁRIO (CONCILIAÇÃO) E SERVIÇO DE SESSÕES
================================================================================

14.1 CashClosingManager.js — Fechamento por período (calendário mensal)

   Distinto do `CashClosure` (DRE, seção 8.3) — este é o fluxo operacional
   de "bater a gaveta física" e conciliar lançamentos, persistido em
   `cash_closings` (um documento por período).

   Regra de agrupamento de período: cada dia é um período isolado, EXCETO
   sábado e domingo, que são agrupados junto com a segunda-feira seguinte
   em um único período (cujo fechamento cobre os três dias).

   Estados visuais por dia: OPEN (sem fechamento ainda), OK (fechado sem
   pendências), PENDING_RED (quebra de caixa — falta de dinheiro,
   prioridade máxima), PENDING_YELLOW (pendência de conciliação — inclui
   detecção dinâmica de novas transações/despesas surgidas após o
   fechamento que ainda não foram reconhecidas).

   Cálculo do saldo esperado da gaveta: vendas em Dinheiro do período menos
   despesas pagas em dinheiro da gaveta (sem conta bancária vinculada).

   Conferência: usuário informa o valor contado fisicamente e uma
   justificativa (obrigatória em caso de sobra). Regras de status:
   diferença > R$0,05 (sobra) exige justificativa, resulta em SUPERIOR_OK
   ou PENDENTE_CONCILIACAO conforme pendências; diferença < -R$0,05 (falta)
   sempre resulta em INFERIOR_PENDENTE (definitivo, mesmo com
   justificativa); dentro da tolerância → OK ou PENDENTE_CONCILIACAO.

   Reconhecimento/conciliação: checkboxes individuais (com "marcar
   todos"/"desmarcar" em lote) sobre despesas em dinheiro e transações
   bancárias do período, salvos como lista de IDs reconhecidos no
   fechamento — sustenta a detecção retroativa de pendência amarela.

   Alertas globais consolidam, no topo, a contagem de quebras vermelhas e
   pendências amarelas em todos os períodos, com a lista de meses/anos
   afetados.

14.2 CaixaService.js — camada de serviço de sessões de caixa

   `checkOpenSession`: verifica se o usuário já tem sessão aberta.
   `openSession`: cria a sessão e, como efeito colateral, RESETA o saldo do
   caixa físico para o fundo de troco informado, vinculando-o à sessão e ao
   operador.
   `closeSession`: fecha a sessão e, se houver `caixaId` (sessões legadas
   podem não ter), reseta o saldo residual do caixa físico e libera seus
   vínculos de sessão/operador para a próxima abertura.
   `addMovement`: registra movimentações (ex.: sangria) vinculadas à
   sessão — não altera saldo por si só, apenas grava o registro.
   O serviço NÃO implementa nenhuma validação de negócio própria (não
   impede sessão duplicada, não valida valores negativos) — toda validação
   fica a cargo de quem consome o serviço (PDV, Configurações).


================================================================================
15. CONTROLE DE DOSES (`DoseManager.js`)
================================================================================

Abertura de garrafa: calcula `maxDoses = floor(volumeGarrafa /
volumeDose)`; decrementa 1 unidade do estoque do produto (consumo físico
da garrafa fechada) e cria um registro de "garrafa aberta" com
`remainingDoses` igual a `maxDoses`. Desabilitado se o produto estiver sem
estoque. Múltiplas garrafas do mesmo produto podem estar abertas
simultaneamente (apenas avisado, não bloqueado).

Venda de doses: quantidade definida pelo operador é enviada ao
carrinho/comanda de destino com preço = preço da dose cadastrado, marcada
`isDose: true` e referência à garrafa de origem. Sem venda bloqueada se
volumes não configurados. Ao chegar a zero doses restantes, a garrafa é
excluída automaticamente e o sistema pergunta se deseja abrir
automaticamente outra do mesmo produto (repetindo o fluxo de abertura, com
nova baixa de estoque). Não há baixa adicional de estoque por dose vendida
— o único ponto de baixa física é a abertura da garrafa.

Descarte de garrafa: exclui o registro sem gerar venda nem estorno de
estoque (a unidade já havia sido baixada na abertura).

Edição de volumes/preço de uma garrafa já aberta: ao alterar os volumes,
recalcula `maxDoses` preservando a proporção de doses já consumidas.

Navegação por teclado dedicada: F12 foca busca; setas navegam entre
garrafas abertas e produtos disponíveis para abrir; Shift+Enter entra em
modo de edição de quantidade; Enter simples vende 1 dose (sobre garrafa) ou
abre nova garrafa (sobre produto); Esc cancela/fecha.


================================================================================
16. COMANDAS (`ComandaManager.js`)
================================================================================

Identificação: nome do cliente (obrigatório) + número de mesa/identificador
opcional (texto livre, sem numeração automática). Todas as comandas de
todas as caixas sincronizam em tempo real entre operadores.

Adição de item de produto: busca por nome/código; quantidade em lote
(inclusive via atalho "5*"/"5x"); item já existente na comanda soma
quantidade, senão cria novo com metadados de quem/quando adicionou.

Adição de dose: reaproveita o fluxo completo do `DoseManager` (seção 15),
mas com destino a comanda em vez do carrinho do PDV.

Seleção de itens para pagamento: cada item marcável individualmente, com
"selecionar todos/nenhum"; total geral vs. total apenas dos selecionados.

Fechamento/envio ao PDV: monta a lista de itens de carrinho a partir da
seleção (preço registrado no momento da comanda, não o preço atual do
produto), com metadados de origem (`tabId`/`tabItemId`) usados depois para
dar baixa apenas nesses itens no documento da comanda (ver seção 6.3, passo
8). A baixa de estoque, o registro de venda e a emissão fiscal ocorrem no
fluxo normal do PDV, não neste componente. Não há transferência de itens
entre comandas.

Cancelamento/exclusão de comanda: exige senha (do usuário logado ou senha
mestra fixa "admin123"); exclusão é permanente, sem estado "cancelado"
intermediário.

17. PERFIS TRIBUTÁRIOS (`TaxRulesManager.js`)
================================================================================

Base: Supabase, tabela `fiscal_tax_profiles`.

Campos: nome (obrigatório, salvo em maiúsculas); CSOSN do ICMS (102, 103,
300, 400, 500 — padrão sugerido para cerveja com substituição tributária,
900); CST PIS/COFINS com 6 opções suportadas — 01 (alíquota normal, exige
informar percentuais de PIS/COFINS), 04 (monofásico/alíquota zero —
recomendado para cerveja/refrigerante/cigarro/combustível, marca
`is_monofasico` automaticamente), 06 (alíquota zero por decreto), 07
(isento por lei — alerta explícito de que para cerveja o correto é 04, não
07), 49 (outras saídas, típico do Simples Nacional), 99 (outras operações);
CFOP dentro do estado e interestadual (com sugestões padrão); origem da
mercadoria (Nacional/Estrangeira direta/Estrangeira mercado interno); notas
livres.

Validação: nome obrigatório; se CST PIS/COFINS = 01, as alíquotas também
são obrigatórias.

Exclusão: avisa que produtos vinculados "podem ficar sem impostos" mas não
bloqueia nem propaga a exclusão em cascata.

Aplicação: cada produto referencia um `taxProfileId`; produtos "filhos"
(pack) herdam o perfil do pai se não tiverem um próprio; no momento da
venda/emissão fiscal, o sistema localiza o perfil e usa seus campos para
montar os tributos do documento.

Aviso de migração: detecta se a coluna `cst_pis_cofins` já existe na tabela
Supabase; se não, orienta rodar a migration SQL correspondente (aviso
dispensável, salvo em `localStorage`).

18. LIBERAÇÃO DE MÓDULOS (`ModulePermissionsManager.js`)
================================================================================

Módulos existentes: Dashboard, PDV & Vendas, Estoque, Parceiros, Notas &
Gastos, Contas a Receber, Financeiro, Precificação, Configurações.

Padrões: role "admin" tem todos os módulos liberados; role "cashier" tem
apenas PDV e Estoque liberados por padrão.

Tela "Por Função" (grupo): toggle por módulo para cada role; módulo
"Configurações" é travado (sempre liberado para admin, sempre bloqueado
para cashier, independentemente do que for marcado na tela).

Tela "Por Usuário (Exceções)": checkbox "Usar padrão do grupo" (se
desmarcado, permite exceções individuais, pré-carregadas com os valores
atuais do grupo daquele usuário); botão "Resetar para grupo"; mesma trava
do módulo Configurações por role.

Log de auditoria: cada alteração (grupo ou usuário) registra
timestamp/autor/mensagem, mantendo as 30 mais recentes por documento;
consolidado numa lista única das 30 entradas mais recentes de todo o
sistema de permissões.

Lógica de precedência efetiva (`canAccess`, consumida em todo o app):
1. Regra fixa: módulo "settings" + usuário admin → sempre liberado.
2. Sem nenhuma configuração salva: admin → tudo liberado; demais → apenas
   PDV e Estoque.
3. Override de usuário (se existir para aquele módulo) tem prioridade.
4. Padrão do grupo/role (se não houver override de usuário).
5. Fallback final: admin → liberado; demais → apenas PDV/Estoque.

Permissões carregadas uma única vez ao montar a aplicação — mudanças feitas
no gerenciador só valem para a sessão do usuário afetado após ele
recarregar a página.

Tela "Acesso Negado": substitui o conteúdo do módulo bloqueado (ícone,
mensagem, botão de voltar ao PDV) — o componente do módulo em si nem chega
a ser montado quando o acesso é negado.

Bypass total: o modo de login "Super Admin" é totalmente independente
deste sistema de permissões (não passa por nenhuma checagem de
`module_permissions`).


================================================================================
19. CONTAS A RECEBER — FIADO (`AccountsReceivable.js`)
================================================================================

Criação do título (a partir de uma venda no PDV fechada com forma "Fiado"
cobrindo ≥99% do total): cria documento em `receivables` com cliente, data
da venda, vencimento, valor, itens, lista de itens reservados,
`status: 'ABERTO'`, histórico inicial. NÃO baixa o estoque definitivamente
— incrementa `reserved_stock` de cada produto vendido (considerando
conversão pack→pai quando aplicável); o estoque físico só é decrementado
na quitação.

Compatibilidade com fiado legado: vendas antigas gravadas diretamente em
`sales` com `paymentMethod: 'Fiado'` continuam aparecendo na listagem,
identificadas com prefixo especial; ações sobre elas gravam campos
diretamente na venda (sem os mecanismos de reserva de estoque, que não
existiam nessa versão anterior).

Cálculo dinâmico de status (recalculado a cada carregamento, exceto os
estados terminais RECEBIDO/CANCELADO): sem vencimento → ABERTO; até 0 dias
de atraso → ABERTO; 1 a 7 dias de atraso → VENCIDO; mais de 7 dias →
CRÍTICO.

Listagem: filtro por status, busca por cliente/id, ordenação por
prioridade (Crítico > Vencido > Aberto > Recebido > Cancelado). Totais: "A
Receber" (Aberto+Vencido+Crítico), "Vencido" (Vencido+Crítico), "Recebido".

Confirmação de recebimento (baixa): sempre integral (não há baixa parcial).
Para título novo: marca RECEBIDO, registra evento no histórico, e dispara a
liquidação completa — cria a venda definitiva em `sales`, dá baixa
definitiva no estoque (decrementa `stock` e devolve `reserved_stock`),
lança `financial_movements` (INCOME, "Recebimento Fiado"), roteia a forma
de pagamento recebida para a conta bancária configurada (mesmo mecanismo do
roteamento de vendas normais). Para título legado: apenas marca campos na
própria venda, sem os efeitos colaterais de estoque/financeiro acima (fluxo
legado mais simples).

Alteração de vencimento: permitida a qualquer momento enquanto pendente,
registrando evento no histórico.

Multa/juros por atraso: aplicação sempre MANUAL (não há cálculo automático
por dias de atraso) — tipo fixo (R$) ou percentual (%), soma ao valor do
título e registra evento no histórico.

Cancelamento: marca CANCELADO, registra evento, e DEVOLVE o estoque
reservado (decrementa `reserved_stock` na mesma quantidade que havia sido
reservada — nunca havia sido baixado do estoque físico). Definitivo, sem
reversão possível.

Histórico de eventos: array anexado (nunca sobrescrito) a cada ação —
CRIADO, RECEBIDO, VENCIMENTO_ALTERADO, MULTA_APLICADA, CANCELADO — com
data, nota e usuário responsável. Títulos legados não têm histórico.

APÊNDICE A — INCONSISTÊNCIAS, BUGS E DÍVIDA TÉCNICA IDENTIFICADOS
================================================================================

Estes pontos foram encontrados durante a leitura literal do código de
produção. São relevantes para a refatoração pois indicam comportamento
REAL diferente do esperado/documentado em alguns fluxos.

A.1 Categorias de Gastos (Configurações): o estado do formulário de nova
    categoria é inicializado como string, mas manipulado como objeto; a
    função de salvar grava o valor bruto (não `.name`) e nunca persiste a
    flag "É Custo Operacional?"; a listagem lê de uma fonte de dados
    diferente da que o CRUD alimenta — categorias recém-criadas podem não
    aparecer imediatamente.

A.2 Perfis Tributários dentro de SettingsManager: existe um conjunto
    completo de estado e funções de CRUD local (não utilizado por nenhum
    elemento da tela renderizada) — código morto que pode ser removido na
    refatoração, já que a aba real delega tudo ao `TaxRulesManager`.

A.3 Senhas de usuário (login de loja e Super Admin) são armazenadas e
    comparadas em TEXTO PURO, sem hashing, tanto no cadastro de usuários
    quanto na exclusão de nota fiscal emitida (confirmação por senha).
    Ponto crítico de segurança a corrigir na refatoração.

A.4 Regime Tributário (CRT) nas Configurações só oferece 2 das 3 opções
    oficiais (falta "Simples Nacional — excesso de sublimite").

A.5 Checagem de duplicidade de login de usuário só ocorre na criação, não
    na edição — um usuário pode ser renomeado para um login já usado por
    outro sem bloqueio.

A.6 `handleSaveCertSettings` (aba Certificado): o `certData.base64` é
    recarregado do banco a cada abertura da tela (não fica vazio por
    padrão), então clicar em "Enviar e Salvar" reenvia o certificado à API
    BrasilNFe mesmo quando nenhum arquivo novo foi selecionado —
    ineficiência, não uma falha funcional (reenvio é idempotente).

A.7 Incompatibilidade de formato entre `FinanceSettings` (produz um array
    de perfis de taxa ricos, com nome e percentual por parcela de crédito)
    e `CashClosure` (espera um objeto simples `{Crédito: %, Débito: %, Pix:
    %}`, sem considerar parcelamento) — a granularidade cadastrada em
    Configurações de Taxas não é de fato usada no cálculo do fechamento de
    caixa como o código está escrito hoje.

A.8 "Fechar Caixa do Dia" (`CashClosure`, DRE) e o "Histórico de
    Fechamentos" associado NÃO persistem em nenhuma coleção do banco —
    ficam em um array de estado local em memória, perdidos ao recarregar a
    página. Adicionalmente, o objeto salvo (`summary`) usa nomes de campo
    diferentes dos que a tela de Histórico e o modal de detalhe tentam
    ler (`total`/`profit`/`sales` não existem no objeto real, que usa
    `totalSales`/`netProfit`/etc.) — a funcionalidade de Histórico de
    Fechamentos, como está implementada, não exibe dados corretos.

A.9 Sobreposição conceitual de pelo menos TRÊS telas de "fechamento de
    caixa"/"caixa" no sistema, com propósitos e fontes de dados distintos
    e não integrados entre si: `CashClosure` (DRE do período, em memória),
    `CashClosingManager.js` (conciliação por calendário, persistido em
    `cash_closings`) e "Relatórios de Caixa" (auditoria histórica de
    sessões `caixa_sessoes`, somente leitura). Candidata forte a
    unificação na refatoração.

A.10 `FinancialReport`: variável `stockPurchases` é calculada mas nunca
    usada no DRE final. O cálculo de CMV por item explicitamente contorna
    "um bug conhecido de conversionFactor para packs" presente no campo
    agregado `sale.cost` — ou seja, há um bug já identificado (mas não
    corrigido na origem) no cálculo de custo agregado de vendas com
    produtos "pack", contornado apenas neste relatório específico.
    Exportação SPED é um esqueleto simplificado (modelo de documento
    fixado em "55" independentemente do modelo real da nota; maioria dos
    campos tributários zerados) — não fiscalmente válido como está.

A.11 Tipo de Movimento "Venda Distribuição" (301) em Entrada de Notas está
    marcado para gerar Contas a Receber (`financialAction: 'RECEBER'`),
    mas o código de geração de parcelas só cobre explicitamente o caso
    `'PAGAR'` — notas de saída/venda por este fluxo não geram
    automaticamente nenhum lançamento de Contas a Receber (lacuna
    funcional).

A.12 Validação de saldo bancário insuficiente ao pagar uma conta é
    inconsistente entre telas: `Transactions.js` (lançamento manual de
    despesa) BLOQUEIA a operação se o saldo for insuficiente;
    `AccountsPayable.js` (baixa manual ou automática de parcelas) NÃO
    bloqueia — debita mesmo deixando o saldo negativo. Regra de negócio
    duplicada e inconsistente entre os dois pontos.

A.13 Exclusão de nota de entrada ou despesa em `AccountsPayable.js` apaga o
    documento inteiro sem reverter efeitos colaterais já aplicados
    (estoque já incrementado pela entrada, saldo bancário já debitado) —
    pode gerar inconsistência de dados residual.

A.14 `getDisplayStock` existe em pelo menos duas implementações
    funcionalmente distintas no sistema: a usada no Dashboard/PDV desconta
    `reserved_stock` (estoque reservado por fiado) do disponível; a usada
    dentro de `InventoryWMS.js` NÃO desconta `reserved_stock` — mesma
    função, comportamento diferente conforme o módulo, o que pode mostrar
    números de estoque diferentes entre telas para o mesmo produto.

A.15 Sangria no PDV aceita uma senha mestra fixa hardcoded ("admin123") como
    autorização alternativa à senha do usuário logado — mesmo padrão em
    Comandas (exclusão de comanda). Backdoor fixo no código-fonte, visível
    a qualquer pessoa com acesso ao repositório.

A.16 Módulo "Contas a Receber" existe na lista de módulos configuráveis em
    Liberação de Módulos, mas não há nenhum botão de menu/checagem própria
    para ele em `App.js` — o acesso à tela ocorre através da permissão do
    módulo "Entradas & Contas" (`transactions`), tornando a permissão
    específica de "Contas a Receber" sem efeito prático isolado hoje.

A.17 Duas fontes de dados de fornecedores coexistem para o módulo de
    Sugestão de Compra: uma carregada localmente dentro de
    `InventoryWMS.js` (Supabase `fiscal_clients`) e outra recebida via prop
    `suppliers` vinda de outro ponto do `App.js` — vale confirmar
    sincronização entre ambas na refatoração.

A.18 Formato de data de venda (`sales.date`, datetime ISO completo) é
    diferente do formato de data de despesa (`financial_movements.date`,
    apenas `YYYY-MM-DD`) — filtros de período em telas diferentes tratam
    esses campos com lógicas de comparação distintas, exigindo atenção ao
    unificar/migrar esses dados.

A.19 Bug de renderização já corrigido durante este levantamento (fora do
    escopo dos agentes, identificado e corrigido pelo assistente): o
    componente raiz `App` não renderizava o componente de notificação
    (Toast) quando em modo Super Admin — qualquer sucesso/erro disparado
    dentro do Painel Super Admin (incluindo o toggle de provedor fiscal)
    ficava setado no estado mas nunca aparecia na tela. Já corrigido em
    ambos os sistemas (DistriPro e VitaGas) nesta mesma sessão de
    trabalho.
